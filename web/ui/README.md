# web/ui — PDT's component library

Spec: docs/superpowers/specs/2026-10-17-design-system-ux-design.md (§3 principles, §4 tokens, §5 inventory, §6 patterns).
Plan: docs/superpowers/plans/2026-10-17-phase-3c-1-design-system.md. Mockup of the kit: the "PDT UX pass" canvas.

## Layout

- `tokens.css` — every colour and token (`--pdt-*`), light and dark. The only place colours are defined.
- `shadcn.css` — shadcn's animations and `data-*` variants (copied from the shadcn package).
- `primitives/` — shadcn/ui components (React Aria base, Nova style), generated by
  `pnpm dlx shadcn@latest add <name> -y -o -c web < /dev/null` (without those it can hang on an overwrite prompt) and then edited to fit. Ours to change. **Features never import these.**
- `lib/` — helpers for the primitives (`cn` in `lib/utils`).
- `<Name>.tsx` — the public components (our API), built on the primitives. `index.ts` exports them; features import
  everything from `@ui`. The one exception is `FlowGraph` (React Flow, for the workflow builder): features import it
  as `@ui/FlowGraph` so it and its styles load only with the builder's lazy chunk. Only web/ui imports `@xyflow/react`.
- `<Name>.test.tsx` — a test per public component.
- Gallery sections: `web/src/gallery/sections/<group>.tsx` (see "Gallery").

## Styling rules

- Colours only through these Tailwind names (all aliases of `--pdt-*`):
  - surfaces: `bg-background` (= `bg-bg`), `bg-card`/`bg-popover` (= `bg-surface`), `bg-surface-2`, `bg-muted` (a quiet fill), `bg-band`
    (striped list rows), `bg-accent` (the soft selected/hover fill), `bg-primary` (accent blue, primary actions);
  - text: `text-foreground` (= `text-fg`), `text-muted-foreground` (secondary text), `text-primary`,
    `text-primary-foreground` (on `bg-primary`), `text-destructive`;
  - lines: `border-border`, `border-input`, `ring-ring`;
  - status (state only, never decoration): `running`, `waiting`, `failed`, `idle`, and fills `running-soft`,
    `waiting-soft`, `failed-soft`; diff: `diff-add`, `diff-del`, `diff-add-strong`, `diff-del-strong`;
  - overlays: `bg-backdrop`; shadows `shadow-popover`, `shadow-dialog`.
- No raw colours (hex, rgb, `bg-black/…`, `bg-white`), no `text-[…px]`, no `z-[…]`. Type sizes: `text-2xs` (10px
  labels), `text-meta` (11px secondary lines), `text-xs` (12), `text-sm` (14), `text-base` (16). Layers:
  `z-(--pdt-z-popover)`, `z-(--pdt-z-dialog)`, `z-(--pdt-z-menu)`, `z-(--pdt-z-toast)`. A test (`src/lint.test.ts`)
  enforces this outside `tokens.css`.
- Sizes: controls are `h-control-sm` (24px) or `h-control-md` (28px, the default); on touch screens
  `pointer-coarse:h-control-touch` (44px) / `pointer-coarse:min-w-control-touch` for icon buttons. Corners
  `rounded-md` (follows `--radius`, 6px).
- Dark mode: `dark:` follows our theme rule; usually no `dark:` is needed because the tokens switch.
- Motion: `duration-(--pdt-duration)` / default transition duration; nothing animates under
  `motion-reduce`.

## Component rules

- **Familiar props.** Public components accept the props features already use: `onClick` (mapped to React Aria's
  `onPress`), `disabled` (→ `isDisabled`), `type`, `title`, `aria-*`, `className` (appended last). Keep the old
  `Button` API working (`variant` primary | secondary | ghost; adds danger; `size` sm | md; `pending`).
- **Accessible by default.** Real roles; icon-only controls require a `label`; every overlay closes on Escape and
  returns focus to what opened it; Up/Down/Home/End in lists and menus; long press = right-click on touch.
- **Touch.** Long press opens the same menu as right-click (`MenuTrigger trigger="contextMenu"`). Drag data is
  `text/plain` with a `pdt:<kind>:<id>` value (Android Chrome drops custom types); draggable rows carry a
  `<Button slot="drag">` handle. Sheets open from a button, never an edge swipe. Never make a long-press target natively `draggable` on touch
  screens (Android turns the long press into a drag): drag from a handle, or only with a fine pointer.
- **Pending and errors.** Actions show `pending` on their control; forms show errors with `Alert`/`Field`; everything
  else toasts (`toast.error(message)`).

## Settings pages

Every settings page (host, project, and whatever comes next) is built the same way from `Page`, `Section` and
`SettingsRow`, so a page reads the same everywhere and nothing destructive sits next to something routine:

- **Page → Section cards → rows.** A `Section` is a heading (and description) over a bordered card; each child of
  the card is a row, divided from the next. Group by what the user is configuring, not by API field; prefer more
  small sections to one long one.
- **One setting per row.** `SettingsRow`: label (and a one-line description) on the left, the control on the right.
  `stacked` for wide controls (text areas, file views, folder fields). State goes in a `Badge`/`StatusDot` in the
  row (Active, Stored, Expired), not in prose.
- **Saving (spec §6.1).** A switch or select saves at once and shows "Saved" beside it. Text fields belong to a
  form: the whole section is the form and its one Save goes in the `footer` (with "Saved" beside it), enabled only
  when dirty. A section saves only its own fields. A lone text field in a section of instant controls (a token, the
  owner) may carry its Save beside it.
- **Buttons are buttons.** In settings every action is a bordered `secondary` button (or `primary` for Save);
  `ghost` is for toolbars, and `Link` is only for navigating somewhere (a URL, another page), never for an action.
  Section-wide actions that change nothing (Check for updates, Run checks again) go in the section's `actions`.
- **Destructive actions live in the Danger zone.** Page-wide removals (remove the project, remove the token) go in
  a `Section danger` at the bottom of the page, as `danger` buttons whose label ends in "…" and that confirm
  (spec §6.2). The one exception is a per-item removal inside a list (a worktree): a secondary button with a trash
  icon, still "…" and confirmed. Never put a destructive button beside a routine one.

## Tests

- Vitest + Testing Library + user-event (`pnpm --dir web exec vitest run ui/<Name>.test.tsx`). Query by role and
  name. Cover: rendering of each variant that changes behaviour, keyboard (open, move, select, Escape), focus
  return, and the touch path where it applies (long press: `fireEvent.pointerDown(el, { pointerType: 'touch' })`,
  advance fake timers past 500ms, `pointerUp`).
- jsdom has no layout: don't assert positions.

## Gallery

`/gallery.html` (dev server only) shows every component. Each group of components adds one file
`web/src/gallery/sections/<group>.tsx` exporting:

```tsx
export const section = { title: 'Buttons', order: 10, render: () => <>…every variant…</> };
```

The gallery picks up every file in that folder by itself (`import.meta.glob`).
