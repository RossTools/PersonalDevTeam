# Personal Dev Team (PDT)

Instructions for coding agents (Claude Code reads this through CLAUDE.md, Codex reads it directly). Humans: start with README.md.

Personal command center for agentic development: tickets + pipeline board, Claude Code / Codex sessions, review, terminals.
Spec: docs/superpowers/specs/2026-10-14-personal-dev-team-design.md. Plans: docs/superpowers/plans/. Roadmap (what comes next, until PDT has tickets): docs/ROADMAP.md — keep it current.

## Workflow (full version: docs/SDLC.md)
- Every change gets its own branch and worktree at `.worktrees/<branch>`, created through the stable PDT so its sessions and Run know it: find the project id with `curl -s 127.0.0.1:7420/api/projects` (match `repoPath`), then `POST 127.0.0.1:7420/api/projects/<id>/worktrees` with `{"branch":"..."}`. That makes the branch (from `main`) and the folder; `cd` in and start. Never commit on `main` in the main checkout.
- A fresh worktree needs `pnpm install --frozen-lockfile` once, and its first cargo build is slow (empty `target/`).
- Before pushing, run the CI checks: fmt, clippy, `cargo test` (commit web/src/api/gen), web typecheck/test/build.
- CI layout (docs/superpowers/notes/ci.md): PR macOS checks run on the Mac mini's self-hosted runner (`~/actions-runner-pdt`, never touch it from a test); Windows checks and bundles run on PRs only with the `windows`/`bundle` label or a change to their files, always on main. Docs-only PRs (only `docs/**` and `*.md`) skip every job but `changes`. Job names are the ruleset's required checks: don't rename them.
- PR against `main`; the user tests the branch with Run → pdt. When the user says merge, turn on auto-merge (`gh pr merge <n> --squash --auto`) instead of watching CI in a shell: GitHub merges once the checks pass. The ruleset requires the branch to be up to date with main; if it falls behind, `gh pr update-branch <n>` (auto-merge stays on). Then clean up (docs/SDLC.md "After merge").
- `gh pr checks` fails with this repo's fine-grained token; use `gh run list --branch <b>`, `gh run view <id> --json jobs`, `gh run watch <id> --exit-status`.
- The stable PDT (7420) runs a release, which can lag main by a version or two: check `curl -s 127.0.0.1:7420/api/health` (`version`) before relying on a new API route or assuming a fix is live.

## Layout
- crates/pdt-core — pure domain types + brand constants (no I/O)
- crates/pdt-git — git CLI wrapper
- crates/pdt-store — SQLite (sqlx) + migrations in crates/pdt-store/migrations
- crates/pdt-agents — PTY terminals (later: structured agent adapters)
- crates/pdt-api — axum routes; errors are JSON {code, message}
- crates/pdt-tailscale — tailscale CLI wrapper (serve, status)
- crates/pdt-update — GitHub release client (token, verified downloads)
- crates/pdt-host — the supervisor: runs pdtd, installs updates, rolls back
- crates/pdtd — daemon binary
- .pdt/project.toml — this repo's run configuration (dev instance + tests)
- web/ — React + Vite UI; web/ui is the design system (tokens.css is the only place colors live)
- desktop/src-tauri — Tauri v2 shell

## Commands
- Rust: `cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt`
- CI runs tests with `cargo nextest run` (every test in its own process, all at once; ~3× faster than `cargo test`). nextest is not installed on the dev machine; plain `cargo test` is the local check. Tests that start servers on PDT-picked ports claim a port block with `test-support/port_blocks.rs`, never a bare random one.
- TS types are generated by `cargo test` into web/src/api/gen — commit them with the Rust type change, or CI's diff check fails.
- Web: `pnpm --dir web dev | test | typecheck | build`
- Run a dev daemon (port 7421, data dir pdt-dev):
  - PowerShell: `$env:PDT_PROFILE='dev'; $env:PDT_SEED='demo'; $env:PDT_WEB_DIR="$PWD\web\dist"; cargo run -p pdtd`
  - Bash (macOS): `PDT_PROFILE=dev PDT_SEED=demo PDT_WEB_DIR=$PWD/web/dist cargo run -p pdtd`
- Throwaway dev daemon for an agent to look at (screenshots, Playwright; Run → pdt needs the user): `PDT_PROFILE=dev PDT_PORT=<free port, not 7420/7421> PDT_DATA_DIR=<scratch dir> PDT_WEB_DIR=$PWD/web/dist PDT_SECRET_STORE=memory PDT_SEED=demo PDT_TAILSCALE_BIN=/nonexistent target/debug/pdtd`. It still launches the real `claude`/`codex` for new sessions (found in their install location even with PATH changed); set `PDT_CLAUDE_PROGRAM` / `PDT_CODEX_PROGRAM` to a stand-in script to avoid that. Stop it by port (`kill $(lsof -ti tcp:<port>)`), never `pkill -f target/debug/pdtd` (that kills other worktrees' daemons). Headless Chromium has no GPU, so WebGL/perf numbers there mean little.
- Never open the stable UI (7420) in a test browser: attaching a terminal resizes the user's real PTY.
- Web conventions are enforced by web/src/lint.test.ts (no raw colours, no arbitrary text sizes or z-index, no `window.confirm`, primitives only inside web/ui): see web/ui/README.md. Web test helpers: `stubApi` / `renderWithQuery` in web/src/test-utils.tsx. Tests that touch the file system need `// @vitest-environment node`.
- The UI polls every 2 s, so components re-render constantly: effects must be idempotent, and never focus from an inline ref callback (use useRef + useEffect). Menus and popovers render in a portal (overflow containers clip them).
- The shell is zsh: quote globs (`grep -r --include='*.ts'`), or zsh fails with "no matches found".

## Running
- A bare pdtd serves no UI unless `PDT_WEB_DIR` is set or a `web/` dir sits next to the exe.
- `pnpm --dir web dev` proxies `/api` to 7421 (the dev daemon).
- `cargo test -p pdt-desktop` and the desktop build need `pnpm --dir web build` first; plain `cargo test` skips the desktop crate.
- Desktop app in dev: `cargo build -p pdtd -p pdt-host`, then `cargo run -p pdt-desktop` with `PDT_PROFILE=dev` and `PDT_WEB_DIR` set (debug builds default to the dev profile when `PDT_PROFILE` is unset).
- The desktop app is an optional tray view of the host (decision 16; no window, no Dock icon on macOS, single instance per profile; a second launch just opens the UI). pdt-host, not the tray, keeps pdtd running. At startup the tray starts pdt-host (`pdt-host run`: the `<data dir>/host` copy if present, else the one beside its exe) when /api/health doesn't answer, then opens the UI. Open (also left-click on Windows) opens `http://127.0.0.1:<port>/` in the default browser. Restart daemon posts /api/shutdown and pdt-host starts pdtd again. The version item shows pdtd's version. Quit exits only the tray; pdt-host and pdtd keep running.
- Releases: every push to main publishes GitHub release `v0.1.<run number>` of ross-game-tools/PersonalDevTeam (`*-setup.exe`, `*.app.tar.gz`), built with that version (pdtd reports it via `PDT_BUILD_VERSION`). PR builds keep the checked-in 0.1.0.
- Update: the tray's Update item follows pdtd's update API (`GET /api/host/update`; a click checks, or installs via `POST /api/host/update/install`, asking again with `force` when the host is busy). pdtd checks GitHub releases with the token stored in the OS keychain (account `update-token` for the stable data dir, `update-token:<hash>` for any other, so a dev pdtd never sees stable's token) and hands the verified download to pdt-host, which installs it, health-checks the new version and rolls back on failure. Updates are offered only when pdt-host supervises a stable pdtd; dev instances never update (and a dev pdt-host never installs). Keychain calls time out after 5 s and the startup token read runs in the background, so a keychain prompt never blocks serving. pdt-host copies the database to `update/db-before-update` before installing and restores it on rollback (an old version cannot open a database a newer one migrated). macOS releases are signed with one certificate (scripts/sign-macos.sh, CI secrets `MACOS_SIGNING_P12`/`_PASSWORD`; notarized by scripts/notarize-macos.sh when `MACOS_NOTARY_KEY`/`_KEY_ID`/`_ISSUER` are set). Today it is self-signed, which has no Team ID, so the keychain partition list trusts each build by code hash and asks again after every update; a Developer ID certificate fixes that (docs/superpowers/notes/developer-id.md).
- Demo data: `PDT_SEED=demo` (set by the "pdt" run) makes a dev-profile pdtd with no projects create two demo git repos in `<data dir>/demo` (branches, a worktree with uncommitted work) and register them with ended sessions and past runs (crates/pdtd/src/seed.rs). Nothing is started; a database with any project is left alone; ignored outside the dev profile.
- Data lives in `<local data dir>/pdt` or `pdt-dev`; a `pdtd.lock` file prevents two daemons sharing a dir.
- `PDT_ALLOWED_HOSTS` (comma-separated) adds Host header values accepted beyond `127.0.0.1:<port>`, `localhost:<port>` and `[::1]:<port>` (DNS-rebinding guard).
- Remote access (Host settings) maps the daemon over `tailscale serve --bg`: the stable instance on https 443, any other port (dev, explicit `PDT_PORT`) on https `<its own port>`. With it off, pdtd runs no `tailscale serve` command (read-only `tailscale status` still runs for the checks); turning it off removes only the mappings that process made. `PDT_TAILSCALE_BIN` sets the tailscale CLI path (tests point it at `fake-tailscale` or a missing file so they never touch the real Tailscale); otherwise it is found on PATH or in the standard install location.
- Remote requests must carry the owner's Tailscale-User-Login (case-insensitive); tagged/Funnel/proxied requests without it get 403 `forbidden_identity`. `PDT_OWNER_LOGIN` sets the owner for dev instances (PDT passes it to every run).
- Runs: "Run" on a worktree/branch starts a `.pdt/project.toml` run on a port from the host's range (stable 8400–8499, dev profile 8500–8599) with its own data folder; this repo's "pdt" run is a dev instance of PDT. Steps run in the checkout (`sh -c` on macOS, a generated .cmd on Windows); only `$NAME`/`${NAME}` of PDT's variables are expanded. Windows command limits and readiness probing: docs/superpowers/notes/phase-2-carryover.md.
- Agent activity: Claude sessions get `--settings <data dir>/sessions/<id>/claude-settings.json` (hooks run `pdtd hook claude <Event>`); Codex gets `-c notify=[pdtd, hook, codex-notify]`. The user's own settings are never edited.
- Workspaces (docs/superpowers/specs/2026-10-17-workspaces-design.md): every project has its own workspace (made with it, deleted with it) plus free-form ones; a workspace is a strip of tabs, each showing one session or run, and a session or run has at most one tab (opening it elsewhere moves it). New sessions/runs open a tab at the end of their project workspace unless the request has `tab: {workspaceId, position}`. The workspace and tab on screen are per browser (localStorage); workspaces and tabs are shared. The Sessions sidebar is herdr-style (web/src/workspaces/Sidebar.tsx): workspaces on top, agent sessions below; tabs, workspaces and agents have right-click menus (long press on touch) drawn in a portal at the pointer. Projects are added and configured in the Settings view. Shortcuts: Ctrl+] then one key (web/src/workspaces/keys.ts), caught on window in the capture phase; Ctrl+] twice reaches the terminal.
- Git integration (workspaces spec §6): projects have a unique key (`PDT`; suggested from the name, backfilled when the store opens); `POST /api/projects/clone` clones into the host's Projects folder (default `~/work`) with `GIT_TERMINAL_PROMPT=0`; removing a project stops its sessions and runs and never touches files. Projects carry `githubRepo` from `origin` (no GitHub API calls). `.worktrees/<branch>` folders made with plain git are adopted; `DELETE /api/worktrees/{id}` refuses while busy (`worktree_busy`) or dirty without `force` (`worktree_dirty`). The Files view reads checkouts through `/api/projects/{id}/files` (git's file list, `.gitignore` honoured; paths stay inside the checkout, `.git` refused).
- Terminals: sessions are PTYs owned by pdtd; they survive closed windows. WebSocket at /api/sessions/{id}/pty; with `?replay=gzip` (the browser asks when it has DecompressionStream) the scrollback replay arrives as one gzip frame.
- Remote speed: pdtd sets TCP_NODELAY on every connection (keystroke echoes are tiny frames), compresses HTTP responses (gzip/br, quality 4), serves `/assets/*` (content-hashed) with `Cache-Control: immutable` and index.html with `no-cache`.
- Terminal input/output in the browser: Shift+Enter sends ESC CR (a line break in Claude Code, Codex, zsh); Compose sends a multi-line prompt as one bracketed paste plus Enter; a mouse selection is copied when the mouse is released, and OSC 52 copies also reach the viewer's clipboard (reads refused); http(s) links (plain and OSC 8; children get `FORCE_HYPERLINK=1`) open on Cmd/Ctrl+click or a tap, and hovering a wrapped OSC 8 link underlines all its rows (web/src/terminal/linkSpan.ts reads xterm's undocumented cell `extended.urlId`); Option+drag selects while the program owns the mouse.
- Agent restart: Claude runs with `--session-id <session id>` and restarts with `--resume <session id>`. Codex cannot be given an id, so each Codex session resumes its own conversation by id: pdtd finds it in `$CODEX_HOME/sessions/**/rollout-*.jsonl` (default `~/.codex`), matches it by working folder and start time against the session's `fresh_started_at` (when it was last launched without a conversation), stores it as `external_session_id` (at process exit or restart) and restarts with `codex resume <id>`. Fresh Codex launches in one folder are spaced 5 s apart so start times stay unambiguous (a create or restart can wait up to 5 s). A session that never took a turn restarts fresh.
- Auto-resume: at startup pdtd decides how to resume every session left `interrupted` (binding Codex conversations) before serving, then restarts them in the background once it is serving (resume mode, 120x30; clients resize on attach; a manual Restart that gets there first wins and auto-resume skips that session; several fresh Codex sessions in one folder start 5 s apart); a session that fails to start stays `interrupted`. Stopped (`finished`) sessions are never auto-resumed.
- Resume fallback: Claude saves `<claude config dir>/projects/*/<session id>.jsonl` only after its first turn. If that file is missing, restart/auto-resume launches `--session-id <id>` (fresh conversation, same id) instead of `--resume`. Config dir is `$CLAUDE_CONFIG_DIR`, else `~/.claude`.
- Terminal reconnect: a terminal that connects while the startup auto-resume has yet to get to its session waits (up to 30 s) and attaches once it starts. The WebSocket for an existing session with no PTY otherwise upgrades, sends `{"type":"not_running"}` and closes; the browser then shows "Session ended." and reattaches when the session list shows it `running` again. Otherwise the browser retries forever (backoff capped at 5 s).
- Logs: <data dir>/logs/pdtd.<date>.log and pdt-host.log; a spawned pdt-host's and pdtd's startup output goes to <data dir>/logs/pdtd-launch.log.
- Worktrees live inside the repo at .worktrees/<branch> (listed in .git/info/exclude). They can be removed from the project's Settings page (or by hand, docs/SDLC.md). A folder there that is not a git worktree for that branch makes Run on that branch fail with `worktree_path_taken`.
- The dev profile also accepts the Vite dev server (localhost:5173) in its Host/Origin allowlist.
- Stable app: scripts/release-stable.ps1 (Windows) / scripts/release-stable.sh (macOS) build the installer (Tauri; pdtd and pdt-host are sidecars via src-tauri/tauri.bundle.conf.json). When pdt-host supervises the stable pdtd they hand the build to it as an update; otherwise they stop the stable tray app and pdtd, install and launch. -BuildOnly / --build-only only builds.
- pdt-host starts at login: `pdt-host install` copies itself to <data dir>/host and registers a LaunchAgent (macOS) or an HKCU Run value (Windows; the NSIS hooks in desktop/src-tauri/windows/hooks.nsh run it). Never run `pdt-host install`/`uninstall` on the dev machine.

## Rules
- TDD for core logic. Tests must pass on Windows and macOS: build fixture paths from `std::env::temp_dir()` ("/srv/code" is not absolute on Windows), and label the PR `windows` for any path, process or file-system change.
- Keep to the asked scope; when the user narrows a request mid-way, do exactly the narrower thing.
- When asking the user to test, point them at the branch's run (Run → pdt on the worktree), not the main checkout's.
- Agents never stop, restart or update the stable instance (port 7420; it hosts the agents building this repo), and never call its /api/shutdown. Only pdt-host and the user's Update do. Never run scripts/release-stable.* without -BuildOnly/--build-only, never run a built installer, and never run `pdt-host install` or `pdt-host uninstall`.
- A dev instance always gets an explicit PDT_PORT and PDT_DATA_DIR: use this repo's "pdt" run (Run → pdt), or PDT_PROFILE=dev (port 7421, data dir pdt-dev) for a manual one. pdtd refuses a data folder another pdtd holds.
- Tests never touch port 7420 or the real data folders, and never the real keychain (PDT_SECRET_STORE=memory).
- Names (product, slug, daemon, ports, release repo, keychain service; also in user-facing UI text) live only in crates/pdt-core/src/brand.rs (+ desktop/src-tauri/tauri.conf.json, desktop/src-tauri/tauri.bundle.conf.json, desktop/src-tauri/windows/hooks.nsh and scripts/release-stable.*).
- Never edit an applied migration (sqlx checksums them); add a new one. Data backfills that run when the store opens (e.g. project keys) go in `Store::open`, not in a migration (tests that build their own migrator skip them).
- On Windows, run cargo from PowerShell, not Git Bash: Git Bash's `link` shadows MSVC `link.exe`.
- The `codex` on PATH may be the Codex desktop app (an old version) shadowing the npm CLI; check `codex --version`.
- New dependencies: add with `cargo add` / `pnpm add` (latest), never versions from memory.
