# Personal Dev Team (PDT)

Instructions for coding agents (Claude Code reads this through CLAUDE.md, Codex reads it directly). Humans: start with README.md.

Personal command center for agentic development: tickets + pipeline board, Claude Code / Codex sessions, review, terminals.
Spec: docs/superpowers/specs/2026-10-14-personal-dev-team-design.md. Plans: docs/superpowers/plans/. Roadmap: this project's tickets in the stable PDT (key `PDT`; `curl -s '127.0.0.1:7420/api/tickets?project=<id>'`, ranked; the Board shows what is picked and in flight). Add or update tickets through the API when work finishes or new work turns up; docs/ROADMAP.md only points there.

## Workflow (full version: docs/SDLC.md)
- Every change gets its own branch and worktree at `.worktrees/<branch>`, created through the stable PDT so its sessions and Run know it: find the project id with `curl -s 127.0.0.1:7420/api/projects` (match `repoPath`), then `POST 127.0.0.1:7420/api/projects/<id>/worktrees` with `{"branch":"..."}`. That makes the branch (from `main`) and the folder; `cd` in and start. Never commit on `main` in the main checkout.
- A fresh worktree needs `pnpm install --frozen-lockfile` once, and its first cargo build is slow (empty `target/`).
- Before pushing, run the CI checks: fmt, clippy, `cargo test` (commit web/src/api/gen), web typecheck/test/build.
- CI layout (docs/superpowers/notes/ci.md): fmt, clippy, tests, TS types and the web checks run on Namespace Linux runners; macOS (clippy, nextest, desktop crate) on a Namespace macOS runner; Windows and the release bundles on GitHub's (the Mac mini's old self-hosted runner in `~/actions-runner-pdt` is unused; never touch it from a test); Windows checks (clippy, nextest) and bundles run on PRs only with the `windows`/`bundle` label or a change to their files, always on main; macOS checks run in the merge queue, on a PR only with the `macos` label or a `.github/` change (most of the Namespace bill); main skips the Linux and macOS checks (the queue just ran them). Docs-only PRs (only `docs/**` and `*.md`) skip every job but `changes`. Job names are the ruleset's required checks: don't rename them.
- PR against `main`; the user tests the branch with Run → pdt. When the user says merge, `gh pr merge <n> --auto` (no `--squash`: the merge queue sets the method) instead of watching CI in a shell: once the PR's checks pass it joins main's merge queue, which runs CI again on main plus the PR and squash-merges it. The branch never needs updating with main; a PR the queue drops (a conflict with main or a failed queue run) needs fixing and merging again. Then clean up (docs/SDLC.md "After merge").
- `gh pr checks` fails with this repo's fine-grained token; use `gh run list --branch <b>`, `gh run view <id> --json jobs`, `gh run watch <id> --exit-status`.
- The stable PDT (7420) runs a release, which can lag main by a version or two: check `curl -s 127.0.0.1:7420/api/health` (`version`) before relying on a new API route or assuming a fix is live.

## Layout
- crates/pdt-core — pure domain types + brand constants (no I/O)
- crates/pdt-git — git CLI wrapper
- crates/pdt-store — SQLite (sqlx) + migrations in crates/pdt-store/migrations
- crates/pdt-agents — PTY terminals (later: structured agent adapters)
- crates/pdt-api — axum routes; errors are JSON {code, message}
- crates/pdt-tailscale — tailscale CLI wrapper (serve, status)
- crates/pdt-github — GitHub CLI (`gh`) wrapper (an attempt's PR, Actions runs)
- crates/pdt-update — GitHub release client (token, verified downloads)
- crates/pdt-host — the supervisor: runs pdtd, installs updates, rolls back
- crates/pdtd — daemon binary
- .pdt/project.toml — this repo's run configuration (dev instance + tests)
- web/ — React + Vite UI; web/ui is the design system (web/ui/README.md): tokens.css is the only place colors live; public components in web/ui/*.tsx exported from `@ui`; shadcn/ui (React Aria base, Nova) sources in web/ui/primitives (ours to edit, never imported by features; add with `pnpm dlx shadcn@latest add <name> -y -o -c web < /dev/null`, which otherwise can hang on an overwrite prompt); app-level shared components in web/src/common
- desktop/src-tauri — Tauri v2 shell

## Commands
- Rust: `cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt`
- CI runs tests with `cargo nextest run` (every test in its own process, all at once; ~3× faster than `cargo test`). nextest is not installed on the dev machine; plain `cargo test` is the local check. Tests that start servers on PDT-picked ports claim a port block with `test-support/port_blocks.rs`, never a bare random one.
- TS types are generated by `cargo test` into web/src/api/gen — commit them with the Rust type change, or CI's diff check fails.
- Web: `pnpm --dir web dev | test | typecheck | build`
- Component gallery: `pnpm --dir web dev`, then `/gallery.html` (dev only, never built). Screenshots for PRs touching web/ui: `node web/scripts/ui-screenshots.mjs <out dir>` (needs `pnpm --dir web exec playwright-core install chromium` once).
- Colour class names follow shadcn: `bg-primary` (accent blue), `bg-accent` (soft selected/hover fill), `text-muted-foreground` (secondary text), `text-destructive`; status colours `running`/`waiting`/`failed`/`idle` are for state only. Merge classes with `cn` from `@ui/lib/utils` (it knows our theme names).
- Run a dev daemon (port 7421, data dir pdt-dev):
  - PowerShell: `$env:PDT_PROFILE='dev'; $env:PDT_SEED='demo'; $env:PDT_WEB_DIR="$PWD\web\dist"; cargo run -p pdtd`
  - Bash (macOS): `PDT_PROFILE=dev PDT_SEED=demo PDT_WEB_DIR=$PWD/web/dist cargo run -p pdtd`
- Throwaway dev daemon for an agent to look at (screenshots, Playwright; Run → pdt needs the user): `PDT_PROFILE=dev PDT_PORT=<free port, not 7420/7421> PDT_DATA_DIR=<scratch dir> PDT_WEB_DIR=$PWD/web/dist PDT_SECRET_STORE=memory PDT_SEED=demo PDT_TAILSCALE_BIN=/nonexistent target/debug/pdtd`. It still launches the real `claude`/`codex`/`devin` for new sessions (found in their install location even with PATH changed); set `PDT_CLAUDE_PROGRAM` / `PDT_CODEX_PROGRAM` / `PDT_DEVIN_PROGRAM` to a stand-in script to avoid that. Stop it by port (`kill $(lsof -ti tcp:<port>)`), never `pkill -f target/debug/pdtd` (that kills other worktrees' daemons). Headless Chromium has no GPU, so WebGL/perf numbers there mean little.
- Never open the stable UI (7420) in a test browser: attaching a terminal resizes the user's real PTY.
- Web conventions are enforced by web/src/lint.test.ts (no raw colours, no arbitrary text sizes or z-index, no `window.confirm`, primitives only inside web/ui): see web/ui/README.md. Web test helpers: `stubApi` / `renderWithQuery` in web/src/test-utils.tsx. Tests that touch the file system need `// @vitest-environment node`.
- The UI polls every 2 s, so components re-render constantly: effects must be idempotent, and never focus from an inline ref callback (use useRef + useEffect). Menus and popovers render in a portal (overflow containers clip them).
- The shell is zsh: quote globs (`grep -r --include='*.ts'`), or zsh fails with "no matches found".

## Running
- A bare pdtd serves no UI unless `PDT_WEB_DIR` is set or a `web/` dir sits next to the exe.
- `pnpm --dir web dev` proxies `/api` to 7421 (the dev daemon).
- `cargo test -p pdt-desktop` and the desktop build need `pnpm --dir web build` first; plain `cargo test` skips the desktop crate.
- Desktop app in dev: `cargo build -p pdtd -p pdt-host`, then `cargo run -p pdt-desktop` with `PDT_PROFILE=dev` and `PDT_WEB_DIR` set (debug builds default to the dev profile when `PDT_PROFILE` is unset).
- The desktop app is an optional tray view of the host (decision 16; no window, no Dock icon on macOS, single instance per profile; a second launch just opens the UI). pdt-host, not the tray, keeps pdtd running. At startup the tray starts pdt-host (`pdt-host run`: on Windows the `<data dir>/host` copy if present, else the one beside its exe; on macOS always the bundle's) when /api/health doesn't answer, then opens the UI. Open (also left-click on Windows) opens `http://127.0.0.1:<port>/` in the default browser. Restart daemon posts /api/shutdown and pdt-host starts pdtd again. The version item shows pdtd's version. Quit exits only the tray; pdt-host and pdtd keep running.
- Releases: every push to main publishes GitHub release `v0.1.<run number>` of ross-game-tools/PersonalDevTeam (`*-setup.exe`, `*.app.tar.gz`), built with that version (pdtd reports it via `PDT_BUILD_VERSION`). PR builds keep the checked-in 0.1.0.
- Update: the tray's Update item follows pdtd's update API (`GET /api/host/update`; a click checks, or installs via `POST /api/host/update/install`, asking again with `force` when the host is busy). pdtd checks GitHub releases with the token stored in the OS keychain (account `update-token` for the stable data dir, `update-token:<hash>` for any other, so a dev pdtd never sees stable's token) and hands the verified download to pdt-host, which installs it, health-checks the new version and rolls back on failure. The web UI reloads itself when `/api/host/update` reports a different `current` version than it loaded against (polled every 2 s while downloading/installing, else every 60 s and on focus); index.html is `no-cache`, so the reload gets the new bundle. Updates are offered only when pdt-host supervises a stable pdtd; dev instances never update (and a dev pdt-host never installs). Keychain calls time out after 5 s and the startup token read runs in the background, so a keychain prompt never blocks serving. pdt-host copies the database to `update/db-before-update` before installing and restores it on rollback (an old version cannot open a database a newer one migrated). macOS releases are signed with one certificate (scripts/sign-macos.sh, CI secrets `MACOS_SIGNING_P12`/`_PASSWORD`; notarized by scripts/notarize-macos.sh when `MACOS_NOTARY_KEY`/`_KEY_ID`/`_ISSUER` are set). Today it is self-signed, which has no Team ID, so the keychain partition list trusts each build by code hash and asks again after every update; a Developer ID certificate fixes that (docs/superpowers/notes/developer-id.md).
- Demo data: `PDT_SEED=demo` (set by the "pdt" run) makes a dev-profile pdtd with no projects create two demo git repos in `<data dir>/demo` (branches, a worktree with uncommitted work) and register them with ended sessions and past runs (crates/pdtd/src/seed.rs). Nothing is started; a database with any project is left alone; ignored outside the dev profile.
- `/api/health` reports `status`, `name`, `version`, `profile` (`dev`/`stable`), `port`, `dev` (dev profile or a non-stable port) and `webBuild` (a 12-hex hash of the served index.html, read per request; null without a web dir); the UI shows a `DEV · <port>` badge in the rail and a `[dev]` title prefix when `dev` is true. The UI polls health every 5 s and reloads when `webBuild` changes from the one it loaded with (a dev instance restarted with a rebuilt web/dist; every dev build reports version 0.1.0), held back while a modal is open or a focused text field holds text (web/src/host/useReloadOnNewBuild.ts).
- Data lives in `<local data dir>/pdt` or `pdt-dev`; a `pdtd.lock` file prevents two daemons sharing a dir.
- `PDT_ALLOWED_HOSTS` (comma-separated) adds Host header values accepted beyond `127.0.0.1:<port>`, `localhost:<port>` and `[::1]:<port>` (DNS-rebinding guard).
- Remote access (Host settings) maps the daemon over `tailscale serve --bg`: the stable instance on https 443, any other port (dev, explicit `PDT_PORT`) on https `<its own port>`. With it off, pdtd runs no `tailscale serve` command (read-only `tailscale status` still runs for the checks); turning it off removes only the mappings that process made. `PDT_TAILSCALE_BIN` sets the tailscale CLI path (tests point it at `fake-tailscale` or a missing file so they never touch the real Tailscale); otherwise it is found on PATH or in the standard install location.
- Remote requests must carry the owner's Tailscale-User-Login (case-insensitive); tagged/Funnel/proxied requests without it get 403 `forbidden_identity`. `PDT_OWNER_LOGIN` sets the owner for dev instances (PDT passes it to every run).
- Runs: "Run" on a worktree/branch starts a `.pdt/project.toml` run on a port from the host's range (stable 8400–8499, dev profile 8500–8599) with its own data folder; this repo's "pdt" run is a dev instance of PDT. Steps run in the checkout (`sh -c` on macOS, a generated .cmd on Windows); only `$NAME`/`${NAME}` of PDT's variables are expanded. Windows command limits and readiness probing: docs/superpowers/notes/phase-2-carryover.md. A run with `detach = true` (PDT-32) starts its command outside any PTY (pdt-agents `detached`: Windows job object, unix `setsid` process group; stdout/stderr to `<data dir>/runs/logs/<run id>.log`, which the Output terminal follows read-only), so it survives pdtd restarts and updates: `resume_runs` reattaches while any of its processes lives (`runs.process`) and marks it stopped otherwise. Format, variables, host overrides, traps and API: docs/run-config.md; to configure a project, use Settings → the project → Runs on this host → Set up with an agent (it starts a session with docs/prompts/set-up-project.md).
- Without the repo (PDT-46): pdtd serves its guides itself, built in with `include_str!` (pdt-api `guides.rs`): `GET /api/guides` lists them, `GET /api/guides/{name}` returns Markdown (`agents` = docs/agent-guide.md, `run-config` = docs/run-config.md, `set-up-project` / `set-up-workflow` = docs/prompts/*.md below their `---` line). Guides link to each other by API path, never by repo path (a test checks). Every agent session (Claude/Codex, terminal or conversation) gets PDT's instructions: a short context block (API address, session, project, checkout, guides; pdt-core `agent_context`) plus the project's **agent instructions** (`project_settings.agent_instructions`, `agentInstructions` in the settings API; kept when a PUT leaves it out, max 16 KB), written to `<data dir>/sessions/<id>/instructions.md`. Claude gets `--append-system-prompt-file <that file>`; Codex terminals `-c developer_instructions=<TOML string>` (through a Windows `.cmd` shim, a pointer to the file), Codex conversations `developerInstructions` on `thread/start`/`thread/resume`; for Codex the user's own `developer_instructions` from config.toml come first, since PDT's value replaces them (pdt-agents `instructions.rs`). The project's Settings page has the instructions box and "Set up with an agent" / "Write instructions with an agent", which start a conversation in the main checkout with the matching prompt.
- Agent activity: Claude sessions get `--settings <data dir>/sessions/<id>/claude-settings.json` (hooks run `pdtd hook claude <Event>`); Codex gets `-c notify=[pdtd, hook, codex-notify]`. The user's own settings are never edited.
- Devin (PDT-54, PDT-55; facts in docs/superpowers/notes/devin-cli.md): a third agent (`AgentKind::Devin`, `devin`, `PDT_DEVIN_PROGRAM`), a conversation by default like the others (`mode: terminal` for its TUI). Terminal: bypass is `--permission-mode dangerous`; the first prompt goes after `--` (a bare argument is a folder to Devin); activity comes from its OSC 7501 status (`app=devin`, the same parser as Codex). Devin has no instructions flag and `--config` replaces the user's config, so each session (terminal or conversation) gets `--config <data dir>/sessions/<id>/devin-config.json`: the user's `~/.config/devin/config.json` (`%APPDATA%\devin\config.json`; JSONC) plus a `SessionStart` hook `pdtd hook devin --instructions <file>`, which prints the instructions as `additionalContext` and, for a terminal, posts Devin's `session_id` (stored as `external_session_id`, latest wins); restart/auto-resume run `--resume <id>`. An unreadable user config means no `--config` (and so no hook). Conversations (PDT-55) run `devin [--config <file>] acp`, one Agent Client Protocol process (JSON-RPC on stdio) per live conversation (pdt-agents `adapter/devin.rs`, mapping in pdt-core `conversation/devin.rs`): `session/new` (its id is `external_session_id`) or `session/load` to resume (its history replay is dropped; a session Devin never saved, i.e. never prompted, gives -32016 and a new one starts with a notice); a turn is one `session/prompt` and a message sent while it runs joins it (steer), Send now cancels first (`session/cancel`); approvals are `session/request_permission` ("Always allow" = `allow_session` only, never Devin's saved rules; a deny note goes as the next message), questions `elicitation/create` (PDT offers the `elicitation.form` capability), plans the exit-plan permission (`plan_accept_edits`/`plan_bypass`); edits carry whole-file old/new text, diffed with `similar`. Devin has no ask-before-edits mode: Ask maps to its Code mode (`accept-edits`), capabilities offer Accept edits / Plan / Bypass and new Devin conversations start in Accept edits. No Make ticket (409 `draft_unsupported`; ACP has no fork). Conversation | Terminal switches like Claude's, one at a time (`POST …/mode`; Devin locks a session to one process): to terminal parks ACP, stores the switch time (ms) in `history_from` and restarts as a terminal (`--resume <id>`); back types `/exit`, then opens ACP at once, whose `session/load` replay imports the turns whose prompt is newer than that time (`source: terminal`; every turn for a session that was always a terminal) and clears `history_from`. Tests use `fake-agent acp`. The host check runs `devin auth status` (exit 0 either way; reads the text) and treats a missing Devin as fine. Web: new-tab "Devin" (d) and "Devin (terminal)" (e), palette "New Devin here" / "New Devin (terminal) here", ticket Start's agent choice, Set up / Write instructions with an agent.
- Offered agents (PDT-55): the new-tab chooser, palette, ticket Start and the project's "… with an agent" menus offer only agents whose host check found them (web/src/common/useAgentAvailability.ts, the `['host-checks']` query Host settings' "Run checks again" refreshes); an installed agent that is not logged in stays with a "not logged in" hint; everything is offered until the checks load or when they fail.
- Workspaces (docs/superpowers/specs/2026-10-17-workspaces-design.md): every project has its own workspace (made with it, deleted with it) plus free-form ones; a workspace is a strip of tabs, each showing one session or run, and a session or run has at most one tab (opening it elsewhere moves it), and closing that tab stops and removes it (`DELETE /api/tabs/{id}`; the UI asks first while it runs; a ticket tab only closes). New sessions/runs open a tab at the end of their project workspace unless the request has `tab: {workspaceId, position}`. The workspace and tab on screen are per browser (localStorage); workspaces and tabs are shared. The Sessions sidebar is herdr-style (web/src/workspaces/Sidebar.tsx): workspaces on top, then Tickets (the workspaces a ticket's Start made, `Workspace.ticket` from `attempts.workspace_id`: ticket title, key chip that opens it, PR badge, agent state; reordered and moved up/down within their own section), agent sessions below; tabs, workspaces and agents have right-click menus (long press on touch) drawn in a portal at the pointer. Projects are added and configured in the Settings view. Shortcuts: Ctrl+] then one key (web/src/workspaces/keys.ts), caught on window in the capture phase; Ctrl+] twice reaches the terminal. The command palette (web/src/palette) opens with Ctrl+] k or ⌘K on macOS (never Ctrl+K: the terminal's kill-line). On phones (< 768px) the list column is a left sheet opened from the workspace name; the rail is Sessions, Tickets, Search (palette), Settings (Files is in the palette's Go to).
- Git integration (workspaces spec §6): projects have a unique key (`PDT`; suggested from the name, backfilled when the store opens); `POST /api/projects/clone` clones into the host's Projects folder (default `~/work`) with `GIT_TERMINAL_PROMPT=0`; removing a project stops its sessions and runs and never touches files. Projects carry `githubRepo` from `origin` (no GitHub API calls). `.worktrees/<branch>` folders made with plain git are adopted; `DELETE /api/worktrees/{id}` refuses while busy (`worktree_busy`) or dirty without `force` (`worktree_dirty`). The Files view reads checkouts through `/api/projects/{id}/files` (git's file list, `.gitignore` honoured; paths stay inside the checkout, `.git` refused).
- Folder picker (PDT-5): `GET /api/host/folders` (`path` absolute or `~…`, empty = home; `hidden`; `nearest` walks up to a folder that exists) lists one folder's subfolders, never files, in the host's path form whatever the browser's OS (pure rules in pdt-core `host_path`, tested for both styles), marking git checkouts and projects; `POST /api/host/folders` `{parent, name}` makes one folder. Web: `FolderField` (web/src/common; path input + Browse… dialog around `@ui` `FolderPicker`) in Add project, Clone → Into folder and Host settings → Projects folder; it writes `~/…` (`~\…` on Windows), which Add project now accepts too.
- Tickets (Phase 4; spec docs/superpowers/specs/2026-10-18-tickets-design.md): per-project numbers that never repeat (`projects.next_ticket_number`; key `<project key>-<n>`), stages draft/ready/todo/in_progress/done/wont_do (Ready is refined but waiting in the backlog; To do is picked for the board), priority, labels (lower-case, no commas), areas (names from the project's `[[area]]` config; see below), a fractional base-62 `rank` (pdt-core `rank`; a new ticket goes to the top of its stage unless `before`/`after` say otherwise), links `blocks`/`relates` (blocks cycles refused with 409 `link_cycle`), and an event timeline (comments are events). Search is FTS5 on title/description keyed by `tickets.seq`, plus exact key/number matches. API: `GET /api/tickets` (`project`, `q`, `stage`/`priority`/`label` as comma-separated lists, `sort` rank|priority|updated|created, keyset `cursor`, `limit`; returns `{items, nextCursor, total}`), `POST /api/projects/{id}/tickets`, `GET|PATCH|DELETE /api/tickets/{id}`, `POST /api/tickets/{id}/rank` (`{before?, after?, to?: top|bottom}`), `POST /api/tickets/bulk` (all-or-nothing), `POST|DELETE /api/tickets/{id}/links`, `GET /api/tickets/{id}/events`, `POST /api/tickets/{id}/comments`, `GET /api/projects/{id}/labels`. A workspace tab holds a session, a run or a ticket (`workspace_tabs.ticket_id`, exactly one). Web: the Tickets view (web/src/tickets; rail item, Ctrl+] l) is the backlog (Draft and Ready unless the Stage filter says otherwise): a virtualised `DataList` paged by cursor (polls every 2 s, every 15 s past two pages), quick add (Enter adds a Draft above the first row when the list is a flat rank order; Shift+Enter opens the full form), filters (saved filters per browser in localStorage), bulk bar, rank by drag or Alt+↑/↓; a row opens the peek sheet (non-modal on desktop, full screen on phones), Open makes a ticket tab. The Board (Ctrl+] b) shows To do / In progress / Done (closed in the last 14 days, `closedAfter`); cards drag between columns on desktop, phones show one column at a time. The demo seed adds 10 Sample App tickets.
- Start (Phase 4b; `POST /api/tickets/{id}/start`, crates/pdt-api/src/start.rs): checks open blockers and overlaps (`mode: check` → 409 `start_blocked`; `force` starts anyway, recorded on the `started` event), makes branch `pdt/<KEY>-<n>-<slug>` and its worktree (adopting one that exists; a new branch starts from `origin/<base>`, fetched first, when that is ahead of the local base), an active attempt (one per ticket, 409 `ticket_active`), moves the ticket to In progress, and starts an agent session (`sessions.attempt_id`; titled with the ticket title) whose first prompt is the ticket (`NewSession.initialPrompt`, appended as the last argv element on the creating launch only; capped at 8 KB). On Windows, when the agent is a `.cmd` shim run through cmd.exe, the prompt goes to `<data dir>/sessions/<id>/prompt.md` and the agent gets a short prompt naming that file. Tabs: the ticket tab, then the session tab after it (or both in a new free-form workspace `<KEY>-<n>`). Sessions carry `ticket {id, key}` (sidebar and tab chips). Session titles never name the agent (a new session is titled with its branch, or the project for the main checkout); tabs, agent rows, the palette and the attempt list show it with `SessionKindIcon` (web/src/common). `POST /api/attempts/{id}/abandon` ends an attempt (worktree kept); moving a ticket to Done ends its attempt as merged, to Won't do as merged if detected, else abandoned. Merge detection (pdt-git `merge.rs`): every 60 s in pdtd's sweep loop and on `POST /api/tickets/{id}/check-merge` (the ticket tab and peek call it on open), fetching each project's base once per tick (`GIT_TERMINAL_PROMPT=0`, only with an `origin`), an attempt is merged when its head (or `attempts.last_head` once the branch is gone) is an ancestor of `<base>`/`origin/<base>` or its whole patch is already there (squash: `commit-tree` + `cherry`), both only once a check has seen the branch hold commits not in the base (`attempts.own_commits`, sticky; PDT-45: a branch that only fast-forwarded to a newer main is not merged), or GitHub says its PR merged at that head (`attempt.pr`; the merge queue squashes onto a newer base, which the patch check can miss). A merged attempt shows the banner "Move to Done and remove the worktree" (web/src/tickets/actions.ts `finishMerged`): after one question it stops every session and run in the worktree, the attempt's sessions and everything in the workspace Start made for the ticket (`attempts.workspace_id`), removes the worktree, deletes that workspace's sessions and then the workspace with its tabs (`DELETE /api/workspaces/{id}?closeTabs=true`), the ticket's among them. Meanwhile it pulls the base branch (PDT-56; `POST /api/projects/{id}/pull {branch?}`, pdt-git `fast_forward`): fetch `origin/<base>` and fast-forward only, in whichever checkout has the branch (`git merge --ff-only`, which refuses rather than touch uncommitted changes) or just the ref; no origin, no branch, diverged, blocked or a failed fetch come back as `outcome` (200), never an error, and the toast says what happened. scripts/import-roadmap.mjs imported the old docs/ROADMAP.md as tickets PDT-1…17 (done once; kept for reference).
- Pull requests and CI (PDT-25; crates/pdt-github, pdt-api `github.rs`, pure rules in pdt-core `pr.rs`): every 60 s (before the merge check) and when a ticket is opened (`check-merge`), pdtd reads each active attempt's PR through the user's `gh` (`PDT_GH_BIN`, else PATH/login PATH, else the standard install folders; tests get `pdt_github::Unavailable` or `testing::FakeGithub`, and pdtd's own tests set `PDT_GH_BIN` to nothing): one GraphQL query for state, draft, mergeable, `BEHIND`, auto-merge, merge-queue entry and newest merge-queue event, then `gh run list --branch` for CI on the PR head (the newest run of each workflow; the fine-grained token cannot read check runs) and, while queued or just out of the queue, the `merge_group` runs on `gh-readonly-queue/<base>/pr-<n>-…`; failed job names come from `gh run view --json jobs` (cached per run attempt). Only projects whose `origin` is on GitHub. The result is in memory and on every ticket response as `attempt.pr` (Attempt section: `PrDetails`; board card: `PrBadge`, web/src/tickets/PullRequest.tsx). Codex cannot be given an id, so each Codex session resumes its own conversation by id: pdtd finds it in `$CODEX_HOME/sessions/**/rollout-*.jsonl` (default `~/.codex`), matches it by working folder and start time against the session's `fresh_started_at` (when it was last launched without a conversation), stores it as `external_session_id` (at process exit or restart) and restarts with `codex resume <id>`. Fresh Codex launches in one folder are spaced 5 s apart so start times stay unambiguous (a create or restart can wait up to 5 s). A session that never took a turn restarts fresh.
- Auto-resume: at startup pdtd decides how to resume every session left `interrupted` (binding Codex conversations) before serving, then restarts them in the background once it is serving (resume mode, 120x30; clients resize on attach; a manual Restart that gets there first wins and auto-resume skips that session; several fresh Codex sessions in one folder start 5 s apart); a session that fails to start stays `interrupted`. Stopped (`finished`) sessions are never auto-resumed.
- Resume fallback: Claude saves `<claude config dir>/projects/*/<session id>.jsonl` only after its first turn. If that file is missing, restart/auto-resume launches `--session-id <conversation id>` (fresh conversation, same id) instead of `--resume`. Config dir is `$CLAUDE_CONFIG_DIR`, else `~/.claude`.
- Terminal reconnect: a terminal that connects while the startup auto-resume has yet to get to its session waits (up to 30 s) and attaches once it starts. The WebSocket for an existing session with no PTY otherwise upgrades, sends `{"type":"not_running"}` and closes; the browser then shows "Session ended." and reattaches when the session list shows it `running` again. Otherwise the browser retries forever (backoff capped at 5 s).
- Logs: <data dir>/logs/pdtd.<date>.log and pdt-host.log; a spawned pdt-host's and pdtd's startup output goes to <data dir>/logs/pdtd-launch.log.
- Worktrees live inside the repo at .worktrees/<branch> (listed in .git/info/exclude). They can be removed from the project's Settings page (or by hand, docs/SDLC.md). A folder there that is not a git worktree for that branch makes Run on that branch fail with `worktree_path_taken`.

- Stable app: scripts/release-stable.ps1 (Windows) / scripts/release-stable.sh (macOS) build the installer (Tauri; pdtd and pdt-host are sidecars via src-tauri/tauri.bundle.conf.json). - pdt-host starts at login: `pdt-host install` registers a LaunchAgent that runs the app bundle's pdt-host (macOS), or copies itself to <data dir>/host and registers that copy in an HKCU Run value (Windows; the NSIS hooks in desktop/src-tauri/windows/hooks.nsh run it). macOS never copies or rewrites the registered program (PDT-40: SentinelOne flags a login item whose program changes as "persistence deception"); after an update pdt-host just restarts from the new bundle. A bundle macOS runs from an App Translocation folder, a folder pdt-host cannot write to (e.g. a disk image) or that has gone is misplaced (PDT-51, pdt-host `placement.rs`): it is never registered at login, `installer_for` refuses it and pdt-host passes the reason to pdtd as `PDT_UPDATES_UNSUPPORTED` (updates then show as off with it); the tray says to move the app to Applications. pdt-host writes its program path to `<data dir>/pdt-host.program`; a tray whose bundle differs from the running pdt-host's offers "switch to this one" (asking at startup when the other copy is misplaced), which runs `pdt-host install --replace` (boots out and stops the other pdt-host, bootstraps this bundle's) and restarts pdtd.

## Rules
- TDD for core logic. Tests must pass on Windows and macOS: build fixture paths from `std::env::temp_dir()` ("/srv/code" is not absolute on Windows), and label the PR `windows` for any path, process or file-system change.
- Keep to the asked scope; when the user narrows a request mid-way, do exactly the narrower thing.
- When asking the user to test, point them at the branch's run (Run → pdt on the worktree), not the main checkout's.
- Agents never stop, restart or update the stable instance (port 7420; it hosts the agents building this repo), and never call its /api/shutdown. Only pdt-host and the user's Update do. Never run scripts/release-stable.* without -BuildOnly/--build-only, never run a built installer, and never run `pdt-host install` or `pdt-host uninstall`.
- A dev instance always gets an explicit PDT_PORT and PDT_DATA_DIR: use this repo's "pdt" run (Run → pdt), or PDT_PROFILE=dev (port 7421, data dir pdt-dev) for a manual one. pdtd refuses a data folder another pdtd holds.
- Tests never touch port 7420 or the real data folders, and never the real keychain (PDT_SECRET_STORE=memory).
- Names (product, slug, daemon, ports, release repo, keychain service; also in user-facing UI text) live only in crates/pdt-core/src/brand.rs (+ desktop/src-tauri/tauri.conf.json, desktop/src-tauri/tauri.bundle.conf.json, desktop/src-tauri/windows/hooks.nsh and scripts/release-stable.*).
- Never edit an applied migration (sqlx checksums them); add a new one. Data backfills that run when the store opens (e.g. project keys) go in `Store::open`, not in a migration (tests that build their own migrator skip them).
- On Windows, run cargo from PowerShell, not Git Bash: Git Bash's `link` shadows MSVC `link.exe`.
- The `codex` on PATH may be the Codex desktop app (an old version) shadowing the npm CLI; check `codex --version`.
- New dependencies: add with `cargo add` / `pnpm add` (latest), never versions from memory.
